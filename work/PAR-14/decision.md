# PAR-14 decision: the purge indexes are written by hand in the generated auth-schema.ts

## Status

Proposed (built 2026-10-03, waiting for the owner's OK)

## Context

The nightly purge (T28, PAR-14) deletes rows by time:

- `session` rows where `expires_at < now`
- `rate_limit` rows where `last_request < now - 24 h`
- `verification` rows where `expires_at < now`

Without an index on that column, each delete reads the whole table every night.
Better Auth's own `rate_limit` prune (`last_request < now - 1 h`) has the same problem.

`packages/db/src/auth-schema.ts` is generated by `pnpm db:auth-schema` from the Better Auth config.
Better Auth 1.7.5 can declare an index on `session` through config, but not on `rate_limit`:
`buildAuthTables` writes the `rateLimit` table after the plugin tables, so an index a plugin adds is overwritten.

## Decision

Add both indexes by hand in `auth-schema.ts`, each with a comment that says so:

- `session_expiresAt_idx` on `session.expires_at`
- `rateLimit_lastRequest_idx` on `rate_limit.last_request`

Migration `0005_purge_indexes.sql` (from `drizzle-kit generate`) creates them.
`verification.expires_at` gets no index: the table stays small, because Better Auth deletes a row once it is used.

**The guard.** A regeneration drops the hand-written lines from `auth-schema.ts`.
The test database is built from the migrations, so it still has the indexes, and the EXPLAIN tests stay green.
That is why `packages/db/test/purge.test.ts` has a schema-level test ("the schema keeps the purge's hand-written indexes").
It reads the indexes from the TypeScript schema (`getTableConfig`) and fails as soon as they are missing.
So `pnpm test` (the gate before each merge) catches the drop before any new migration can remove the indexes.

## Alternatives considered

### Leave the tables without indexes

- Pros: `auth-schema.ts` stays 100% generated.
- Cons: every purge and every Better Auth prune reads the full table.
- Rejected: the item asks for the indexes.

### Put the indexes in `schema.ts` or a hand-written SQL migration only

- Pros: the generated file stays untouched.
- Cons: Drizzle can only declare an index inside the `pgTable` call of its table.
  A migration without a schema entry makes `pnpm db:check` fail, and the next `drizzle-kit generate` writes a `DROP INDEX`.
- Rejected.

### Wrap `pnpm db:auth-schema` so it adds the indexes back after generating

- Pros: no manual step after a regeneration.
- Cons: a script that patches generated TypeScript text breaks when the generator's output changes.
- Not done now. Possible later if regenerations become frequent; the test already makes a drop visible.

## Consequences

- After any `pnpm db:auth-schema`, put the two index lines back. The purge test fails until you do.
- `0005` uses a plain `CREATE INDEX` (Drizzle runs each migration in a transaction, so `CONCURRENTLY` is not possible).
  It blocks writes to `session` and `rate_limit` while it builds during the deploy. Both tables are small today.
- Neither `pnpm test` nor `pnpm db:check` runs in a GitHub workflow today; both are local gates. A dropped index is caught by the schema-level test in `pnpm test`.

## Open for the owner

1. Is the hand edit in the generated file acceptable, or do you want the wrapper script?
2. `rate_limit` rows are kept 24 h (24x the 1-hour guest window). 2-3 h would also be safe if you want the table smaller.
